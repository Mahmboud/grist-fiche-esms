Administration MOAD

Travailler le projet Grist avec une IA sans exposer de données individuelles

Le principe est simple : toutes les données individuelles sont centralisées dans CONTACTS. Les autres tables doivent référencer CONTACTS plutôt que recopier des noms, prénoms ou emails. Quand CONTACTS est épurée dans une copie de travail, les données individuelles disparaissent des vues liées.

🧭 Procédure pour démarrer une nouvelle version de travail

Dupliquer la version Grist de productionDans Grist, créez une copie du document et renommez-la avec le préfixe VERSION TRAVAIL_.
Épurer les données individuelles dans la copieDans cette copie, ouvrez l’onglet 💾 Sauvegarde & restauration, sauvegardez CONTACTS si nécessaire, puis lancez l’épuration.
Vérifier la copie avant de la transmettreTéléchargez la version de travail et vérifiez manuellement que noms, prénoms, emails et autres données individuelles ne figurent plus dans le document.
Travailler uniquement sur cette version avec l’IALes modifications de structure, ACL, widgets, formulaires et ergonomie sont réalisées sur la copie épurée.

💾 Sauvegarde

Avant toute épuration, conservez toujours :

  • une sauvegarde complète .grist ;
  • un export intégral de CONTACTS.
Le fichier de production reste la référence métier. La copie IA n’est jamais la seule copie disponible.

♻️ Restauration

La restauration de CONTACTS sert principalement à réinjecter les identités dans une copie privée de test. Pour une vraie mise en production, il faut aussi tenir compte des données métier qui ont évolué pendant le développement : Autodiagnostic, ESMS, référentiels, etc.

Ne pas faire de l’ancienne VERSION TRAVAIL la nouvelle production sans resynchroniser les données métier récentes.

🚀 Passage en production recommandé

Pour éviter des exports/imports table par table, je recommande un gel très court uniquement au moment du basculement, pas pendant toute la période de développement.

1. Production continue normalement
Pendant que la VERSION TRAVAIL évolue avec l’IA, les professionnels continuent de saisir dans la production.
2. Au moment du déploiement : courte fenêtre de gel
Prévenir les utilisateurs et suspendre les modifications pendant quelques minutes afin d’obtenir un état cohérent.
3. Faire immédiatement une nouvelle duplication de la production
Cette copie contient alors les dernières données CONTACTS, Autodiagnostic, ESMS et tous les autres enregistrements à jour.
4. Appliquer les évolutions du modèle sur cette duplication fraîche
L’objectif est de migrer la structure et les widgets, et non de recopier manuellement toutes les données métier.
5. Tester puis basculer
Contrôler les ACL, les formulaires, quelques contacts et quelques Autodiagnostics avant de réouvrir les accès.
Pourquoi cette méthode ? Elle évite d’avoir à réimporter séparément CONTACTS, Autodiagnostic, ESMS et les autres tables. La duplication fraîche de production apporte naturellement toutes les données à jour ; seule la couche modèle doit être migrée.

⏱ Faut-il interrompre l’accès ?

Pas pendant le développement. Une interruption courte est utile seulement lors du basculement final, pour éviter qu’un utilisateur modifie la production entre la dernière copie et l’ouverture de la nouvelle version.

🧩 Ce qu’il faudra automatiser ensuite

La prochaine amélioration logique est un mécanisme de migration du modèle : appliquer à une duplication fraîche de production les évolutions de structure réalisées dans VERSION TRAVAIL, sans transporter les données individuelles vers l’IA.
